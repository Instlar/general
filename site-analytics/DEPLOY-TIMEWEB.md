# Размещение готовой админки «Мои сайты» в Timeweb Cloud

**Это уже существующее приложение, не новый сайт.** Исходники: `Instlar/general`, ветка `healthy-baking-v1`, директория `site-analytics/`.

## Почему сейчас нет публичного адреса

`site-analytics` — сервер Node.js + SQLite и админка по адресу `/admin`. Публикация соседней директории `healthy-baking/public` **не запускает** сервер `site-analytics/server.mjs`. Сам по себе исходный код GitHub не является живой страницей.

### ВАЖНО: постоянная база

По документации Timeweb Cloud, данные **внутри контейнера App Platform удаляются при повторном деплое**. Админка сейчас хранит посещения в SQLite. **Нельзя** ставить её на обычное App Platform с локальным `DB_PATH=./data/analytics.sqlite` и включать сбор реального трафика: статистика может исчезнуть.

Для этой версии используйте отдельный процесс на **Timeweb Cloud Server / VPS с постоянным диском** (или уже существующий VPS для сайтов, с отдельным непривилегированным пользователем и своей директорией базы). Не смешивайте базу с «Тугарином».

Если будет выбран App Platform, сначала потребуется поддержка внешней постоянной базы и миграция схемы — текущая SQLite-версия для этого не готова.

## Настройки уже готового приложения

- Node.js **24 LTS**, допустимо 22.13+.
- Корень: `site-analytics`.
- Команда: `npm start` (или `node server.mjs`).
- Проверка здоровья: `GET /healthz` → `{"ok":true}`.
- Админка: `https://<домен-админки>/admin`.
- Предустановленные проекты: `baking` — «Здоровая выпечка»; `plants` — «Комнатные растения».
- Код счетчика: `https://<домен-админки>/tracker.js` с атрибутом `data-site="baking"` или `data-site="plants"`.

### Секреты (только на сервере)

`ADMIN_PASSWORD` — длинный надежный пароль (минимум 16 символов).
`SESSION_SECRET` — независимый случайный секрет минимум 32 символа.
`HOST=127.0.0.1`
`PORT=4301`
`DB_PATH=/var/lib/site-analytics/analytics.sqlite`
`TRUST_PROXY_HTTPS=1`

Пароль и секрет **никогда не писать в GitHub, frontend или чат**. Настраивайте их в защищенном файле окружения на VPS, например `/etc/site-analytics.env` с правами `0600`, принадлежащем пользователю root. Для `systemd` этот файл читается менеджером служб. Если задаете переменные иначе, защитите их от просмотра другими пользователями.

Убедитесь, что пользователь `site-analytics` может записывать только в `/var/lib/site-analytics`, а каталог базы хранится на постоянном диске и входит в резервное копирование (файл SQLite и WAL/SHM; предпочтительно горячий backup SQLite). Не удаляйте базу при обновлении.

## Пример развертывания на VPS (для администратора хостинга)

1. Установить Node.js 24 LTS и настроить HTTPS reverse proxy (Caddy или Nginx).
2. Создать пользователя `site-analytics` без входа в оболочку, каталог с приложением и отдельную директорию постоянных данных.
3. Взять каталог `site-analytics` из ветки `healthy-baking-v1`; установить права чтения на код.
4. Настроить переменные окружения выше. Не копировать `.env.example` с заглушками как рабочий пароль.
5. Запускать через `systemd` (пример `deploy/site-analytics.service`), без выдачи приложению root-прав.
6. Проксировать HTTPS с выбранного домена админки на `http://127.0.0.1:4301`. Использовать действительный сертификат. **Не открывать порт 4301 публично**.
7. Проверить `GET https://<домен-админки>/healthz`; открыть `/admin`, войти, убедиться, что в списке два сайта.
8. В настройках «Здоровая выпечка» указать `https://pekizdorovo.ru` (и WWW-версию только если используется). Аналогично добавить точный адрес сайта растений.
9. Вставить в **общий шаблон** каждого сайта его код подключения из кабинета. Для «Здоровой выпечки» это `healthy-baking/tools/render.py`, после чего пересобрать `healthy-baking/public`. Не подключать счетчик к несуществующему адресу.
10. Дополнить политику конфиденциальности: случайный ID хранится в localStorage, посещения и активная видимость страницы отправляются на собственный сервер статистики. Не заявлять, что нет аналитики, после подключения.
11. Проверить раздельный счет посещений обоих сайтов, источники, обновление страницы и повторное посещение. Административные `/api/admin/*` должны отдавать 401 без авторизации.

### Проверка работы локально

Из `site-analytics`: `npm test`. Тесты запускают временную SQLite-базу, проверяют логин, разрешенные источники, изоляцию сайтов и подсчет посещений.

## Чего НЕ делать

- Не публиковать admin.html отдельно в корень сайта: он зависит от защищенного API.
- Не давать администраторам общий пароль игры или доступ к игровой базе.
- Не использовать несуществующие URL-адреса или подставные данные.
- Не запускать боевой сбор посещений на временной файловой системе.
- Не считать подключение готовым, пока ссылка `/admin` реально не открывается по HTTPS, а оба сайта не отправляют события.
